# WRSR Industrial Tycoon — technical guide

These are the implementation and investigation notes previously kept in the README. They include historical version details. For current features, installation and gameplay instructions, start with the [project README](README.md).

Goal: production and freight transport without citizen management. Buildings and infrastructure are purchased with money.

Initial target: the existing oil refinery, supplied with oil and electricity, operates without citizens. Input consumption, outputs and storage limits must remain correct.

Status: refinery production with zero workers confirmed by user screenshot (48% output). Woodcutting without workers confirmed by the user after installing 0.2. Road vehicle production without workers/engineers confirmed by the user after installing 0.3. Version 0.4 adds every power plant (type 17), confirmed in game by the user on 16-oct. Version 0.5 adds a staff-free fire service; the user confirmed in game (16-oct) that fire trucks dispatch and fight a fire without firefighters, and the log showed the virtual-crew extinguishing counter rising. Version 0.6 admits the staffed ship buildings (drydock, ship scrapyards), version 0.7 the train factories, version 0.8 the container facilities and version 0.9 the food, alcohol & crops section (food factories, distilleries, livestock farms, slaughterhouses, synthesized fertiliser, hand-worked fields) and version 0.10 the miscellaneous section (sawmill, fabric and clothing factories, gravel quarry and processing, cement, concrete, prefab panel, asphalt and brick plants, every woodcutting post); version 0.11 admits industries by type instead of by name, so Workshop buildings are covered too; version 0.12 lets vehicle repair stations repair without staff versions 0.13 and 0.14 let construction offices use concrete and asphalt plants without staff as sources; version 0.15 covers waste management and water management for games that enable them (waste chain factories, water wells) and the airport control tower; version 0.16 adds the water and sewage treatment plants; their in-game validation is pending. Maximum output, supply-stop and save/load checks of the industries remain pending. The separate construction add-on (0.20) builds every storage except the waste ones, the small farm, electric buildings, traction transformers, power lines, steam (cooling) pipes, construction/demolition offices, roads (incl. street lights, bridges, tunnels, surfaces, footpaths), road buildings (depots, gas stations, parking, cargo stations, and since 0.16 vehicle repair stations), fire stations, the whole ship section (harbors, ship docks, drydock, ship scrapyards) and the rail section (rail depots, train stations, train factories, rail distribution offices, rail construction offices, and rail tracks built by staff-free rail construction offices), the cargo & storage section (distribution offices, container facilities, forklift station and crossing, cableway, factory connections) and the conveyor section (conveyors, bulk conveyors, engines/transfers, overpasses) with every pipe, the trees & accessories section (monuments, fences, fence gates, pergolas, colonnades) the food, alcohol & crops section (every farm, fields and its factories) the miscellaneous section and, since 0.15, every factory (except the waste chain), mine, production line and scrapyard with any name, so Workshop industries build too, and since 0.17 the airport section (runways, taxiways, stands, heliports, the airport road connection, the control tower), customs houses, the foreign pipeline connection, the waste chain and the water and sewage networks, without workers, since 0.18 renovates admitted buildings with virtual workers when building wear is on, since 0.19 lets construction offices deliver asphalt to road sites that only virtual workers will lay (confirmed in game on 18-oct), and since 0.20 lets the realistic terrain tools work the ground by hand with virtual workers when no excavator, bulldozer or unemployed citizen is available (electric buildings and power lines confirmed in game). Project notes and in-game test steps are kept in the local, unversioned AGENTS.md.

Known local installation: `F:\SteamLibrary\steamapps\common\SovietRepublic`.

Supported-build investigation: `SOVIET64.exe`, PE timestamp `0x6A3EB6AD`, SHA256 `296644A9F207D609031FC2AE73FED2DCB34619A1D55A35D1C7B51965CE6841B8`.

The prototype must reject unknown builds and unexpected instruction bytes. Development and tests use copies of the executable; runtime experiments use a separate, disposable save.

## Implementation and evidence

- Factory production: RVA 0x1D1E80 calls work-factor routine 0x175A00 at 0x1D213A before recipe processing.
- The work-factor routine assigns normalized local [RBP+0x6F] to 1.0 for definitions with no workers or professors, at 0x175CF0.
- Our patch at 0x175CF7 replays one complete five-byte MOVSS and sets that local to 1.0 only for factory type 6, localized name 6053, 500 workers, zero professors.
- Version 0.2 also admits woodcutting: type 7, extraction kind 4, localized name 7001, 10 workers, zero professors. The mine tick at 0x1B392D calls the same work-factor function. For wood, 0x1B39F2 calls 0x1B3CE0 with that factor; 0x1B3D4D multiplies it by the configured staff before applying wood yield and updating forest operations. Tree availability and vehicle collection remain in the original code.
- Water, weather and wear logic remain downstream. Their actual effect on the prototype still needs in-game validation.
- Version 0.3 admits road vehicle production: type 40, localized name 2020, 400 workers and 100 engineers. The parser at 0x10E928 assigns production-line type 40. Its tick at 0x1CA020 calls the same labor function at 0x1CA151; the original 0x178FE0 recipe planner and 0x17A7B0 resource application remain unchanged. Work/engineer normalization selects their minimum before our hook, so substituting the final normalized local covers both staff classes. Vehicle selection, licenses, resources and assembly progress still require the original game conditions.
- Version 0.4 admits every power plant: descriptor type 17 (parser 0x10EF29), any name/staff. The factory routine branches on type 17 at 0x1D2015 and still calls the labor function at 0x1D213A, so only the final normalized factor changes; fuel, cooling towers, wind/sun and water logic stay original. The labor stub grew to 258 bytes, so its capacity is now 512 and the generator is bounds-checked.
- Version 0.5 adds an optional fire service module (`fire_service`, `virtual_firefighters` in the INI; a mismatch only skips this module). Dispatch: the station selection 0x253060 (called from 0x13E8EF, fire-station branch after type 0x1A at 0x253418) accepted road trucks only when the station's people list (+0xBC0..+0xBC8) was non-empty; the `jne` at 0x25373E becomes `jmp` (helicopters were already accepted). Extinguishing: the building fire update 0x13EC60 multiplies each truck's rate by its crew (vehicle +0x4C8..+0x4D0) and skips empty trucks. A 115-byte stub at 0x13F165 keeps the original path for staffed trucks; for an empty truck it uses the truck's own fire skill value (skill entry +4, accepted in [1, 100], else `virtual_firefighters`), replays the rate/counter updates without the per-firefighter fatigue loop and continues at the fire-point reduction 0x13F22E.
- Version 0.6 admits every building whose subtype is SHIP: $SUBTYPE_SHIP writes 0x13 to descriptor+0x364 (parser 0x10FAE4). Only two ship buildings have staff: the drydock (production line 0x28, 400 workers + 100 engineers; every production line goes to 0x1CA020 from 0x13DD98) and the ship scrapyards (type 0x6D, 150/90/280 workers; the dispatcher calls 0x14B920 at 0x13E1C9, and that tick calls the labor function at 0x14BAA4 and uses the result as its work rate). Road, rail and aircraft factories (subtypes 25, 26, 33) and the aircraft scrapyard stay excluded.
- Version 0.7 also admits every building whose subtype is RAIL ($SUBTYPE_RAIL writes 0x1A at 0x1187EB): the train factories (production line 0x28, 400+100 and 200+50 staff) are the only staffed ones.
- Version 0.8 adds an optional container facility module (`container_facility` in the INI). Container facilities (type 0x2C, parser 0x10F310; packing and unpacking, 60 workers) do not call the labor function: their tick 0x1C27F0 (dispatcher 0x13E329) sums the work of the people present (+0xBC0..+0xBC8) into XMM13, at most 1.0 per person (efficiency 0x1BCAE0 x (qualification 0x18FE20 x 0.7 x productivity 0x824290 + productivity x 0.3)), and the rest of the tick spends XMM13 on containers. With nobody there it stays 0. A 102-byte stub at 0x1C2A6A, where the empty-list branch (0x1C2933) and the end of the loop meet, sets XMM13 to the facility's $WORKERS_NEEDED (descriptor+0x80C) when no work was summed, then replays the stolen `cmp [r14+0x5bc],r12d` so the flags stay original.
- Version 0.9 replaces the refinery's exact check (name 6053, 500 workers, 0 professors) with a table of factory names admitted with any staff, one menu section at a time: 6053 refinery, and for food, alcohol & crops 6101 food factory, 6102 distillery, 6104 livestock farm, 6105 slaughterhouse and 7573 synthesized (liquid) fertiliser. The bio-waste fertiliser (7572) belongs to the waste chain and stays out. The labor stub is 335 of 512 bytes.
- Version 0.16 adds the water and sewage treatment plants ($TYPE_WATER_TREATMENT 0x61, parser 0x10E8B6; $TYPE_SEWAGE_TREATMENT 0x62, 0x10E8DC; 10/20 workers) to the labor stub's admitted types. They do use the labor factor: the dispatcher selects both with `sub ecx,0x61; cmp ecx,1; ja` at 0x13DD24-0x13DD38 and calls 0x1CE9A0, which calls 0x175A00 at 0x1CEA80 and feeds the factor to the factory production plan (0x1797A0, 0x1760E0, 0x17A7B0), so consumption, electricity, chemicals and water quality stay original. (0.15 had missed this path: it searched only `cmp [desc+0x360],imm` dispatch patterns; the Codex audit found it.) The labor stub is 173 bytes.
- Version 0.15 follows the user's decision of 17-oct to cover waste management and water management, for games that enable them (heating stays out). Factories are admitted by type with any name, the waste chain included (incinerators, waste separation, recycling, bio-waste fertiliser, toxic waste treatment); the labor stub drops to 147 bytes. The work-site module gains three per-site fields (staff field, people counter register, stack copy of the work) and two sites: control towers ($TYPE_AIRPLANE_TOWER 0x30, 15/20 engineers, no workers): tick 0x1C23C0 sums the engineers' work into XMM8 and counts them in R14D, then raises or lowers the tower's operating level (+0x11A8, capped at $PROFESORS_NEEDED); the hook at 0x1C25CF (relocated `cmp [rbp+0x5bc],r15d`, where the empty-list branch and the loop end have met) sets XMM8 = R14D = $PROFESORS_NEEDED when nobody worked; water wells ($TYPE_MINE_WATER 0x5C, 7 to 10 workers): tick 0x189030 calls 0x1B1290 (its only caller), which sums the workers' work into XMM15 and [rsp+0x74]; the hook at 0x1B14C6 (relocated `cmp [r14+0x5bc],r15d`) sets both to $WORKERS_NEEDED. Water pumps, endstations and sewage pumps have no staff; no use of the water and sewage treatment plants' staff was found in the simulation (only their network connection and water quality code), so their operation without workers is pending an in-game check. Technical services have no staff.
- Version 0.14 completes the plant sources module. The construction office tick has two versions, chosen by the byte [game+0x14455] at the dispatcher 0x13E139: 0x146B10 when it is set, 0x145900 otherwise. Version 0.13 only patched the routine used by 0x145900 and by the office window, so in a game running 0x146B10 the warnings disappeared but the office still sent no mixer or dumper to the plants (with customs as the source it did). 0x146B10 picks sources through 0x155960, which takes a customs house (type 0x14) directly and calls 0x151780 for a concrete plant (source kind 3) and 0x151910 for an asphalt plant (kind 4); both return false when the plant needs staff ($WORKERS_NEEDED + $PROFESORS_NEEDED) and nobody is present, before checking its inputs. The `jne` after that test (0x1517C0, 0x151950) becomes `jmp`, so the input check decides, as for the other routine. Plant loading itself never needed staff: a depot truck with a manual route loaded asphalt at the plant and sold it at customs. A temporary diagnostic used to find this (0.13.1, 0.13.2) is removed.
- Version 0.13 adds an optional plant sources module (`plant_sources` in the INI; a mismatch only skips this module). A construction office warned "The concrete plant can't produce concrete" and "The asphalt plant can't produce asphalt" (strings 1623/1625) although both plants were producing without staff and had output ready. The office routine 0x1561C0 (office tick 0x145900 and the office window) walks the office's sources (+0xF78..+0xF80, 16 bytes: building, kind). For a concrete plant source (kind 3, checked at 0x156E08) or an asphalt plant source (kind 4, 0x156FBF) that is not a customs house (type 0x14), it checks the plant's inputs and then keeps it as the plant that can produce only when its people list (+0xBC0..+0xBC8) is not empty (`cmovne` at 0x156FA0 and 0x157150). Without it the office warns and never sends its mixers and dumpers there. Both `cmovne` become `mov` + `nop`, so the input checks stay and the people test goes. The concrete plant (6168) and the asphalt plant (6169) are type 6 factories with 5 workers, already producing without staff through the labor patch.
- Version 0.12 adds an optional repair station module (`repair_station` in the INI; a mismatch only skips this module). Vehicle repair stations are $TYPE_REPAIR_OFFICE 0x6C (parser 0x10EE6B): the small, medium and large stations (15/30/80 workers), the base-game repair service office (50) and the DLC3 stations, including the horse wagon one (10 workers + 10 engineers). Their tick 0x14C5B0 (dispatcher 0x13E1A9) walks the repair jobs (+0xFF0..+0xFF8, 0x48 bytes each, people per job at +0xC) and gets each job's rate from 0x1AD790 (only caller 0x14C992), which sums the productivity of up to that many people of the station's people list (+0xBC0..+0xBC8), starting after the people already serving earlier jobs; with nobody left it returns 0, so a station without people never repairs. A 125-byte stub on the `jge` at 0x1AD7DF keeps the original paths when people are present; with an empty list it sets the rate to the virtual people left for the job (the station's `$WORKERS_NEEDED` minus the people per job of earlier jobs, at least one, at most the job's people) and continues at the game's building condition factor (0x1AD897, 0x1AA280). The tick also skipped the job loop with nobody present unless the station flag +0x11C1 was set (it is set when a station is created, 0x2D7251, and arms the jobs' idle timers); the `jne` at 0x14C8A8 becomes a 6-byte NOP, as when people are present. Vehicle admission does not depend on people: a vehicle picks a station by its +0x11C0 flag, completion and free capacity (+0xDEC, which is `$WORKERS_NEEDED` at creation, minus the people per job of the current jobs, 0x1AE870).
- Version 0.11 replaces the name tables with building types, because Workshop buildings that use `$NAME_STR` instead of `$NAME` (for example "Gravel Mine v2", a `$TYPE_MINE_GRAVEL` with 50 workers) have no base-game name id and never matched. Admitted with any name and staff: mines (type 7, every extraction resource), production lines (0x28: road, rail, ship and aircraft factories), scrapyards (0x6D) and power plants (0x11), plus every factory (type 6) except the waste chain names 7557, 7558 (incinerators), 7561, 7562, 7563 (waste separation), 7564, 7565, 7570, 7571 (recycling), 7572 (bio-waste fertiliser) and 7598 (toxic waste treatment). The SHIP and RAIL subtype rules stay. The labor stub drops to 318 bytes. Both plugins now take their version from a single `#define` used by the plugin info and the startup log (construction 0.12 to 0.14 logged a stale `v0.12.0`), and `dev.py` checks it against its own version.
- Version 0.10 adds the miscellaneous section to the factory table (7002 sawmill, 6351 fabric, 6352 clothing, 6158 gravel processing, 6170 cement, 6168 concrete, 6172 prefab panels, 6169 asphalt, 6171 bricks) and turns the woodcutting check (name 7001, extraction kind 4, exactly 10 workers, so the 5-worker DLC3 posts were left out) into a table of mine names admitted with any staff: 7001 woodcutting post and 6155 gravel quarry (40/100 workers). Every $TYPE_MINE_* is type 7 with its extraction resource at descriptor+0x368 (stack 0x1E18); the mine tick 0x1B3700 calls the labor function at 0x1B392D. The labor stub is 461 bytes and its capacity grows to 1024. The gravel recycling plant (7565) belongs to the waste chain and stays out.
- Version 0.9 also generalizes the container facility module into `src/work_stub.h`: buildings whose tick sums the work of the people present (+0xBC0..+0xBC8) instead of calling the labor function, described by a table of sites (relocated instruction, building register, work register, building type). Hand-worked fields (type 8, parser 0x10E9C8; 75/150/250 workers) are the second site: tick 0x16E3B0 (dispatcher 0x13E0D9) sums the productivity 0x824290 of each rested person into XMM6 and advances the field by XMM6 / [field+0xE30] (0x16E564); the empty-list branch (0x16E466) and the end of the loop meet at 0x16E4FD (`mov rcx,[rsi+0xe68]`, relocated). When no work was summed, XMM6 = the field's $WORKERS_NEEDED. Each site has its own INI key (`container_facility`, `fields`). Farms (type 9) have no staff: their vehicles work the crops.
- The type parser's $NAME writes stack offset 0x1CB0 and $TYPE_* writes 0x1E10. The latter corresponds to descriptor offset 0x360, giving name offset 0x200. Normalization reads workers/professors at 0x80C/0x810.

The copied executable and disassembly remain private research files, excluded from release packages.

## Validation and build

`dev.py verify` checks the copied executable's SHA256, architecture, timestamp and complete patch instruction.

`dev.py test` executes the emitted x64 stub and the actual DLL on synthetic memory. It checks target selection, zero-staff substitution, register/flags preservation, MOVSS semantics, jump bounds, unsupported builds, changed instructions, disabled state, late conflicts and allocation failure.

These tests do not establish real production rates, input consumption, storage behavior or save/load behavior. In-game validation remains required.

Python environment: .venv (capstone, pefile). Compiler: tools/llvm-mingw-20261006-ucrt-x86_64. Upstream source: vendor/TesmioLoader.

Commands: dev.py build, dev.py test, dev.py loader, dev.py probe, dev.py package, dev.py update.

License: GPL-3.0-or-later. Locally rebuilt loader packages include the upstream license and complete source.

## Construction add-on

industrial_construction.dll 0.20 hooks 0x15A39D inside the construction routine 0x159070 (RDI=building, ESI=accepted workers, XMM7=summed productivity). With zero accepted staff it substitutes up to `virtual_workers` (50) equivalents, capped by building+0x62C. The stolen MOVD/CVTDQ2PS still run; materials, phases, machinery and progress remain original. Funded (+0x608/+0x609), maintenance ([RBP+0x240]), completed (+0x604 >= 1) and staffed sites are untouched.

The stub (table-driven since 0.6: building type -> family, road type -> family) is 1286 of 2048 bytes with eighteen family counters plus the renovation counter, preserves flags/RAX/RCX and is emitted by a bounds-checked generator. The user confirmed in game (16-oct) the substation, several power line types, towers, coal/gas/solar/wind power plant construction, steam pipes and traction transformers, and (on a new map) rail buildings and rail tracks built by a rail construction office with no staff: the log showed its vehicles working at rail sites with a virtual crew. Offices, roads, fire stations and ships are pending.

Rail tracks (0.9, optional `rail_construction` module): rail segments (road type 1) never reach 0x15A39D; the construction routine diverts them at 0x1594AD and lets the first vehicle in the site's +0xC70 list work them. 0x66BD60 refills that vehicle's crew (+0x4C8..+0x4D0) from the people present at its rail construction office (home +0x4F8, type 0x1C, people list +0xBC0), shared by vehicle capacity (skill +8); skill 27 vehicles are automatic (0x66BD30) and need no crew. With nobody at the office the summed crew productivity (XMM9) stays 0. A stub at 0x159657 (end of the crew loop, reached by je from 0x1595DF) gives an empty vehicle of a rail office with skill 22, 26 or 28 a virtual crew equal to its capacity scaled by office staff (+0x80C) / office vehicle capacity (+0xDEC), the share the office would give when fully staffed (fallback `virtual_track_crew`, 20). The rail office tick 0x1403F0 refuels parked vehicles (0x142430) only while it has more people present than the vehicle index; the `ja` at 0x142345 becomes `jmp`. Staffed vehicles keep the original code.

Asphalt delivery (0.19, part of the construction patch, no INI key): virtual workers are added at 0x15A39D, when the site is worked, but the construction office decides earlier whether to deliver asphalt at all. Its delivery planner 0x14EB10 (RBP game, RBX site, R14 resource; callers 0x14FCAA, 0x1502B6, 0x15053A) handles an infrastructure site (+0x5D0 set) that asks for asphalt ([game+0xC298]+8) in an asphalt phase (phase kind 8; phase index from 0x14DDE0, phases at +0x610, 0x21B8 bytes each) like this: it skips the delivery (0x14F110) when the trip value from 0x1544A0 exceeds 35, or when no office assigned to the site has an asphalt paver (0x1528E0, which walks the site's offices +0x880..+0x888) and none can bring real workers (0x1521F0 with the workers resource [game+0xC2C8]). A road with no paver available (none exist in 1920 starts) and no workers source therefore never got its asphalt, and the site waited at "Laying asphalt" with "Missing resources: Asphalt" (reported by the user on 18-oct in an early-start game; the save showed 12 office dumpers, none with an asphalt trip). The patch replaces the final `je 0x14F110` at 0x14EC50 with a jump to a 213/512-byte stub: when an office can bring real workers it continues as before; otherwise it plans the delivery (0x14EC56) only when the construction stub will give the site virtual workers (an admitted road type, a worker maximum +0x62C of 1..5000, not funded with RUB or USD) and skips it otherwise. The trip limit and the paver check stay original, and buying, transporting and consuming the asphalt are unchanged. RAX and the flags are dead at both targets; dev.py checks the 103-byte context from 0x14EBEF, both targets and that no branch of 0x14EB10 enters the patched instruction. A separate counter logs `asphalt: deliveries planned for virtual workers=N`. A related gate in 0x14F160 (sending mechanism kinds 3 and 4 to a site with nobody present needs 0x1521F0 too) is left original: it only decides whether those machines are sent.

Terraforming (0.20, optional `terraforming` module, `virtual_terraform_workers`, default 100, range 1..1000): in realistic mode the terrain tools (the terrain tool 0x3A8A70 with its five modes, and the brushes in 0x2BADE0 and 0x4FCAF0) call the terrain work planner 0x3A6FD0 (RCX game, RDX selected terrain points, R8D skill: 3 `$SKILL_GRAVELMINING` for excavators, 0x17 `$SKILL_CONSTRUCTION_BULLDOZER`, R9D vehicle limit). It copies the points (12 bytes each) to [game+0xD2D8..0xD2E0] and selects vehicles with that skill whose home is a completed depot (type 0x0E) or construction office (type 0x0C, only with vehicle +0x50C <= 0) within 1800 of the selection into [game+0xD2F0..0xD2F8], adding their skill power to [game+0xD374]. When it selected none, it counts unemployed citizens of nearby residential buildings (type 2) and labour halls (type 1) into [game+0xD338], at most one more than the points, and adds count/3 to the power. With no vehicle and a count of 0 the callers show "You need a free excavator (bulldozer) in depot or construction office (or unemployed citizens in residential buildings or labour halls)" (strings 1169/1171 and 25175) and leave the ground as it is. Otherwise they change the terrain a little every frame from that power and count (the brushes work as many points per frame as there are vehicles or citizens, each at power/count/70; the terrain tool spreads the total power over the selection), and the preview draws worker figures for the citizens. No excavator or bulldozer is available before 1956-1957, and Transport Tycoon games have no citizens, so realistic terraforming was impossible there. A 113/256-byte stub at 0x3A77E3 replaces `mov eax,0x55555556`, the start of the count/3 step where the citizen loop and its empty-building-list branch (0x3A7621) meet: when no vehicle was selected it raises the count to min(`virtual_terraform_workers`, points), keeping a larger real count, then replays the instruction, and the game turns the count into power as for citizens. So the ground changes gradually at the game's manual-labour rate: 100 virtual workers give 33 power, about one and a half early excavators (power 22). The paid RUB/USD modes, the vehicle search, its range, the gate in 0x3A7880 and the warning for other causes are untouched; no citizen, vehicle or material is created. RAX, RCX, RDX and the flags are dead at the site; dev.py checks the 89-byte context from 0x3A77B3, the citizen search entry, the planner tail, that RCX is written before any read after the patch, that no branch enters the patched instruction, and the four callers with their warnings. A counter logs `terraforming: tool updates with virtual workers=N` (it rises every frame the tool works with the virtual crew).

Build/test/package/install this add-on with dev.py construction-build, construction-test, construction-package and construction-install. The existing industrial_tycoon.dll is not replaced.

## Building from source

The repository contains plugin source and tests. It does not include the compiler, TesmioLoader source, a Python environment or the game's executable. Build on Windows x64, from the repository root.

### 1. Prepare the dependencies

Install Python 3.10 or newer and Git, then create the Python environment:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

Fetch the TesmioLoader revision used by this project:

```powershell
git clone https://github.com/MaxLegend/TesmioLoader.git vendor/TesmioLoader
git -C vendor/TesmioLoader checkout 3baa141f9f08921aea9c95f0a400289cabd9960a
```

If that dependency is already present, check its revision rather than cloning over it. Install the **UCRT x86_64** toolchain from [LLVM-MinGW](https://github.com/mstorsjo/llvm-mingw/releases). The current build script expects:

```text
tools/llvm-mingw-20261006-ucrt-x86_64/bin/clang++.exe
```

Use that directory layout, or update `CLANG` in `dev.py` to your toolchain location.

### 2. Supply your own game executable for verification

Copy `SOVIET64.exe` from your own WRSR **1.1.1.9** installation to `research/SOVIET64.exe`. The build checks its SHA256 and patch instructions before compiling. A different game executable will be rejected.

This is a private local verification input. Keep it out of commits, packages and releases; the repository and release archives do not supply it.

### 3. Build and verify both plugins

Run each command separately:

```powershell
.\.venv\Scripts\python.exe dev.py loader
.\.venv\Scripts\python.exe dev.py build
.\.venv\Scripts\python.exe dev.py test
.\.venv\Scripts\python.exe dev.py construction-build
.\.venv\Scripts\python.exe dev.py construction-test
.\.venv\Scripts\python.exe dev.py package
.\.venv\Scripts\python.exe dev.py construction-package
.\.venv\Scripts\python.exe dev.py release
```

The tests execute native code on synthetic memory; they do not launch the game. The two plugin packages are written to `dist/`. `release` checks their hashes and builds the player archive `dist/wrsr-industrial-tycoon-v<release>.zip`. It holds only the `tesmioloader` folder: the loader, the launcher, both plugins, their INI files and the GPL license. The release number is `RELEASE` in `dev.py`, separate from the plugin versions. The source for the release binaries is this repository at the release tag and TesmioLoader commit `3baa141`, unmodified, built with `dev.py loader`. Install its `tesmioloader` folder as described in the [README](README.md#install).

The `install`, `update` and `construction-install` helpers currently use the maintainer's local game path in `dev.py`. For another machine, use the manual installation steps or adapt those paths first. Do not replace DLLs while the game is running.
